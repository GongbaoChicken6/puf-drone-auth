# 提示词工作流：根据综合/实现报告定位瓶颈

> 类型：提示词工作流 ｜ 适用：任何 Vivado 工程的"资源/时序为什么不行"诊断
> 使用记录：本队 W1/W2/W3 迭代中反复使用的诊断流程整理（配合
> collect_report.py 的产物）；同样属于"流程走通"级别。

## 何时用

- report_utilization / report_timing_summary 出来后，数字不达标或想优化。
- 里程碑前，要向报告输出"优化过程（优化前后对比表）"。

## 失效条件

- 综合都没过的工程（先解决 ERROR）。
- 试图把综合后 WNS 当签核结论（见红线；签核必须布线后报告，UG906）。

## 提示词模板

```
角色：你是 FPGA 性能/资源诊断工程师。以下是我的真实报告数据：

<粘贴 collect_report.py 生成的 metrics .md，或原始 report 片段>
工程背景：<顶层功能、目标时钟、器件、流水目标 II=?>

请按以下顺序诊断，每步先给结论再给证据（引用具体数字）：
1. 资源：哪一类资源逼近上限？按 hierarchy 表找出最贵模块，
   区分"算法必需"还是"实现选择"（如过多暂存、过宽乘法器）。
2. 时序：违例是 setup 还是 hold？WNS 集中在哪个时钟域/哪些路径组？
   给出 report_timing -max_paths 3 的 Tcl 让我自己跑。
3. 对照我的目标：给出最多 3 个按"收益/工作量"排序的修改建议，
   每个注明：预期改善（定性+依据）、风险、验证方法（跑什么命令、
   看什么数字）。
红线：
- 只允许基于我贴的数据下结论，缺的数据列清单向我要；
- 综合后时序数字必须标注"估算"；
- 不许建议"降低时钟频率"来收时序，除非我明确允许。
```

## 输出怎么用

1. 第 3 步的每条建议实施后，重新 collect_report.py，把前后两个 .md
   都贴回给 agent：`这两份是修改前/后，验证你的预测是否成立`。
2. 预测不成立的条目，让它解释原因——这一轮解释经常暴露真正的
   瓶颈（比如实际是拥塞不是逻辑级数）。
3. 前后 metrics .md + 这轮对话存进 `report/`，就是竞赛要求的
   "优化过程含前后对比表"的原始材料。
