## 一、协作模式与智能体工作流设计(Agent Workflow Design)

### 1.1 总体模式

六周开发全程采用**"AI 生产、AI 交叉审查、人类决策"**的协作模式,三条协作线并行:

| 线 | 前缀 | 内容 | 运行工具 |
|---|---|---|---|
| 核心开发线 | c01–c13 | 硬件设计、认证协议、基站软件、板卡 bring-up | DSH 智能体团队(指挥 AI + 队友 AI + 子代理) |
| 前端可视化线 | f01–f03 | three.js 地面站监控界面 | Claude Code(前端作者队友) |
| 技能包线 | s01–s02 | Vivado MCP 工具链、可复用技能封装 | mathmodel 内嵌 Claude Code 兼容 CLI |

人类(队长)的角色:**决策、板卡物理操作、读灯观察、最终验收**;AI 的角色:方案起草、实现、交叉审查、诊断。

### 1.2 指挥—派发—审查架构(核心开发线)

核心开发线使用"团队指挥 AI(lead)→ 派发子任务 → 多代理独立审查 → 共识汇总"的结构:

- **派发**:lead 会话把工作拆成自包含子任务(带文件路径、基准 commit、输出格式),派发给独立上下文的子代理。全周期累计 **153 次派发**(口径:导出时会话摘要的派发记录计数;逐会话分布 c01:37 / c03:18 / c05:40 / c06:17 / c07:4 / c09:19 / c10:6 / c11:12),派发以交叉审查为主、兼有开发实现——raw 底档中留存的代理回报告主题即为实证,如 "Plan Review — Round 1:Verdict FAIL"(raw/c01)、"defect-reviewer … FAIL"(raw/c05)、"silent-failure-hunter 审查完成"(raw/c05)、"极性污染全量盘点报告"(raw/c11)。
- **五角度并行审查**:一个会话完成实现后,改动分派给多个互相独立的审查 AI,分别从**功能缺陷、是否符合设计约定、该失败时是否被静默放过、数据类型与数据宽度、测试覆盖**五个角度并行审查,再汇总形成共识结论;只有全部严重问题清零才判定通过(对应报告图 3-12)。
- **复审规则**(防止"审查盖章"空转):修复后必须派 Round 2 复审,且**复审代理必须对每个"已修"项给出本轮新证据**,最多 3 轮(原文,raw/c11 [10-23 10:23] 第6轮):

> 收到审查报告后:按 P0→P1→P2→P3 修正计划 → 派 Round 2 复审(复审代理必须对每个"已修"项给出本轮新证据)→ 最多 3 轮 → 出具最终报告。

- **严重度分级**:审查发现按 P0(阻断)/P1(严重)/P2/P3 分级,双方证据引文相同=同源命中按单源,证据独立=高可疑(共识去重规则写进审查技能说明,raw/c11 [10-23 10:22])。

### 1.4 三条线的工具栈与人机分工

- **核心开发线(DSH)**:团队指挥 AI 编排子代理;审查产出按"前提成立与否"复核(见 §三 T4 的教训)。
- **前端可视化线(Claude Code)**:设计用 brainstorming 技能展开;实现采用**截图 + 视觉模型评审 + 人工验收**闭环——用户要求"多截图取用视觉模型看看做的到底怎么样"(raw/f03 [10-15 21:30] 第20轮),实现侧回应:"先截图+视觉评估现状,找出『交互感差』的具体病灶,再动手改,改完用截图对比复验"(raw/f03 [10-15 22:09] 第20轮),共 ≥5 轮 UI 升级。
- **技能包线(MCP 驱动)**:用 vivado-mcp-server 以标准接口真实驱动 Vivado(握手 → 11 工具注册 → 拉起 → get_parts → 真实综合 → 真实 xsim 仿真 → 优雅关闭,7 项自动判分),而不是纸面检查。
- **人机分工原则**(bring-up 夜定型):物理域操作(上电/插线/按键/读灯)由 AI 发"操作单"给用户——**动作 + 预期现象 + 异常即停**;本案例最终的定性证据正是用户人眼读灯(见 §三 T3)。

> **【提示词 · 全文】**
>
> 看完理解后在需要的地方用上新工具继续下个S2
> 【本机效率工具通告：你有两个可直接调用的 MCP 服务，干活前先看这条】
>
> 你正在这台机器（Windows）上协助 FPGA 项目开发。本机已配置好两套 AMD Ross MCP 服务，能让你的工作质量和效率大幅提升：①本地 Vivado MCP（直接驱动 Vivado 跑 Tcl：建工程、综合、时序/资源报告、开关会话）②AMD 官方文档检索 MCP（按文档编号/版本精确命中官方手册小节，附 docs.amd.com 直链）。请把下面的用法纳入你的工作方式：涉及 Vivado 的操作优先通过 MCP 实测验证，涉及 Vivado/Vitis 方法论的问题先查官方文档再回答。
>
> ━━━ 服务 1：Vivado MCP（本地，实操通道）━━━
> 端点：POST http://127.0.0.1:18090/mcp（协议：MCP Streamable HTTP，即 JSON-RPC 2.0 over HTTP）
> 若连接被拒（守护进程空闲约 5 分钟会自退，属正常），用以下命令拉起后重试：
> & 'C:\Users\<user>\.vscode\extensions\amd.vivado-ai-extension-2026.9.1\bin\vivado-mcp-server-windows-amd64-2026.9.1.exe' --background --env=VIVADO_LICENSE_MODE=auto --env=MCP_CLIENT_TYPE=vscode --env=VIVADO_STATE_DIR=C:\Users\<user>\.vivado-ai
> 握手流程（服务端有客户端门禁，务必照做）：
> 1. POST {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{"tools":{"listChanged":true}},"clientInfo":{"name":"claude-code","version":"2.0.0"}}}
> ⚠ clientInfo.name 必须用标准客户端名（claude-code 实测通过）；自造名字会返回 0 个工具。
> 记录响应头 Mcp-Session-Id，后续请求都带此头。
> 2. POST notifications/initialized（无 id，带会话头）
> 3. tools/list → 11 个工具：vivado_start / vivado_execute / vivado_status / vivado_stop / vivado_list_sessions / vivado_connect / vivado_history / vivado_log_messages / vivado_cleanup / vivado_todos / vivado_client_info
> 4. tools/call：{"name":"vivado_start","arguments":{"session_type":"general","working_dir":"<纯英文目录>","vivado_path":"D:\\vivado\\2026.1\\Vivado\\bin\\vivado.bat"}}
> 再 {"name":"vivado_execute","arguments":{"session_id":"<返回的id>","command":"<Tcl，简单命令用分号批量>"}}
> 关键规则：
> - working_dir 必须纯英文——中文路径会让 synth_design 崩溃（0xC0000374，本机实测）
> - 综合等长命令单独一条发；若连接超时，Vivado 仍在跑：轮询 vivado_status 的 is_command_running，结束后读 last_completed_code
> - 会话空闲会自动退出属正常；结束用 vivado_stop
> 高效用法示例：写完 RTL 后直接让 MCP 跑 synth_design + report_timing_summary，把 WNS/资源数字拿回来再改代码，不要凭空猜。
>
> ━━━ 服务 2：amd-doc-search（官方文档检索，知识通道）━━━
> 端点：POST https://ross.amd.com/mcp/doc-search（握手同上，无需 key）
> 工具：vivado_doc_search，参数注意——tool 与 version 是**数组**：
> {"name":"vivado_doc_search","arguments":{"query":"timing closure methodology report_timing_summary","tool":["Vivado Design Suite"],"limit":3}}

## 三、自我纠错轨迹(Self-Correction Traces)

八条主要轨迹,按时间排列。叙事立场:**用户驱动 AI 创作,并对 AI 结果有选择地接受**——AI 的方案与修复只有在用户的验收、实测或复核通过后才落地,被否决的产出同样留档。共同结构:**现象 → AI 初判 → 用户把关点 → 实证翻案 → 修正与回退成本 → 沉淀为规则**。

### T1|混淆应答方案被可执行攻击证伪(10-07,c03)

## 四、技能包提炼过程(Skill-Pack Distillation)——经验如何变成可复用资产

### 4.0 提炼方法论

技能包定位:**把与大模型协作过程中沉淀下来的经验显式提炼出来,供他人直接复用**。指南(3.3.5.2)要求说明每项技能"从哪些失败或观察中总结得出",因此每项技能都按同一条管线提炼:

**失败/观察(会话与复盘留档)→ 通用化规则(去项目化、改写为"动作+通过判据+失败处置"祈使句)→ 门禁化(可机读的 PASS/FAIL 与退出码)→ 离线测试(pytest 正反用例)→ 边界标注(失效条件显式写入)→ 来源标注(【本队实测】/【文献】/【文档+本队】不混淆)**

**用户在提炼中的角色**:验证规矩由队长定立——"真实驱动、绝不冒充已测、待板项显式标注"(技能包线开工时即明确"按队长的要求用 MCP 真实驱动 Vivado……不是纸面检查",raw/s02 第1轮;✅/⏳ 二值状态表即其落地);技能的取舍与叙事口径由用户审定(T1 的两次否决与自研拍板、T5 的工时复核与换板决策);调研立项与"从哪些失败或观察中总结"的出处要求,也是用户对照评分细则提前布置的工作项。

两个真实的"原材料→规则"转化示例(出自迁移复盘,极性翻案 T3 的直接沉淀):

- 失败:"事实卡写『按键空闲=1/按下=0(来源 UG954 Table 1-29)』——该表只有引脚号与 IOSTANDARD,极性只在电路图里" → 规则:"事实卡每条标注证据等级 [A 官方文字表格]/[B 官方图纸推断]/[C 板文件]/[D 厂商参考设计]/[E 板上实测];**极性/激活电平/空闲态=[E] 唯一放行**"
- 失败:"第 50 分钟我就基于未实证的根因写完修复并烧上板" → 规则:"根因分假说与实证两级,**只对实证级写修复**;必须带假说工作时按豁免条目五要素建档(时限/撤销条件/安全代价/仿真锁定/跟踪任务)"

### 4.1 调研先行:为什么是这五个技能

2026-10 的技能生态调研(raw/c02)扫描了 skills.sh 全站 sitemap(约 2 万条目)、anthropics/skills 官方库、awesome 列表与 GitHub/Gitee:**没有成熟的通用 PYNQ skill**——现有 FPGA 类 skill 集中在 Vivado Tcl/RTL 仿真/约束(AMD Ross 官方 51 个亦然),PYNQ 主机侧(overlay 体检、DMA 纪律、契约生成、报告收割)是空白。技能包即按此空白设计,四个技能对应选题指南 3.3.5.2 列举的全部四个正例方向,第五个(板卡迁移)由本队真实换板需求驱动。

### 4.2 五个技能的提炼过程(出处→提炼→验证→边界)

#### S1. pynq-overlay-load-verify(Overlay 加载与校验)

- **从哪些失败/观察总结**:C 线 bring-up 期间多版本位流/诊断副本高频迭代(仅 10-22 一晚就 9 轮诊断构建、多个 bitstream 先后上板),".bit 与 .hwh 不同源、IP 改名后主机代码失配"是 overlay 侧最高频的事故模式——地址表对不上位流,寄存器写进去就是错的。观察收敛为事故模式表(SKILL.md 内 Common errors)。
- **如何提炼**:把"上板前体检"流程化为 `overlay_doctor.py`——静态模式在 PC 上秒级解析 .hwh(REGISTERS 节点,与 pynq `hwh_parser` 同一数据源),对 .bit/.hwh 时间戳不同源直接告警;live 模式上板做寄存器写回读。
- **如何验证有效**:离线测试 T1/T2——合法 overlay 判 PASS 并正确解析出 IP/基地址/寄存器数;**故意删掉 .hwh 的反例必须判 FAIL**(exit=1,"no .hwh sidecar" 告警),防止检查器本身静默放过。
- **边界如何确定**:仅 .tcl 元数据的老式 overlay(静态检查警告);无 AXI-Lite 的纯流式 IP(live 模式跳过并说明)——失效条件写入 SKILL.md,不装作全能。

#### S2. pynq-dma-coherence(DMA 搬运与缓存一致性)

- **从哪些失败/观察总结**:这是**观察+文献交叉**型出处:PS 侧缓存纪律(flush before send / invalidate after wait)是 DMA 类设计最隐蔽的失效源,错误表现是"数据偶发错乱"而非报错。提炼时没有轻信模型记忆,关键 API 事实(DMA TLAST 语义、2^14 传输上限)经 PYNQ 文档与 `pynq/lib/dma.py` 源码逐条核对,缓存失效模式对照 UG585 整理,并归纳为**错误指纹表**(按数据模式直接定位失效类:缓存纪律/流未通/错位)。
- **如何验证有效**:离线 T7——`--dry-run` 打印完整调用序列核对纪律(tx.flush() 在 sendchannel.transfer 之前、rx.invalidate() 在 wait 之后首次读之前);板上数字诚实标注"待本队 DMA 里程碑回填",不编造基准。
- **边界如何确定**:UltraScale+(CCI+dma-coherent)上为无操作但保留可移植性;仅覆盖 simple 模式,Scatter-Gather 显式声明未覆盖;没有可回环 AXI DMA 的 overlay 直接拒绝并说明。

#### S3. pynq-interface-contract(接口契约 → 主机代码/测试骨架)

- **从哪些失败/观察总结**:本队**手写 MMIO 偏移两次出错**(W 系列 PS 侧驱动开发中,寄存器偏移手写与 RTL 实际漂移不符)+ RTL 接口演进而主机代码没跟上的教训——把接口契约变成"生成物与测试物",让人手不再抄写偏移。
- **如何提炼**:契约 JSON(寄存器+操作)+ .hwh(真实基地址)→ `gen_driver_stub.py` 生成 driver + pytest 骨架;离板跑逻辑测试(FakeMMIO),上板跑 `-m board` 冒烟。
- **如何验证有效**:T3/T4——合成 HLS 风格契约生成-测试闭环 pytest 全绿,且含**"坏寄存器必被检出"的反向测试**;IP 名与 .hwh 不一致时生成器警告而非静默用 0。
- **边界如何确定**:复杂位域打包(子字段结构)暂不生成 accessor(写整字),显式声明。

#### S4. pynq-golden-report(黄金比对 + 性能/资源自动报告)

- **从哪些失败/观察总结**:W1/W2/W3 轮次报告收割实践的脚本化;叠加本队"指标必须从工具原始输出收割、禁止手改"的铁律教训(gen_metrics 事件:手工修饰过的指标数字一旦出现就不可信,全部改为从 `report_* -file` 原始文本机读)。
- **如何提炼**:`golden_compare.py`(CSV/向量/二进制、容差门禁、行列数不匹配判 FAIL、退出码供 CI)+ `collect_report.py`(utilization 含 -hierarchical、timing_summary → 单文件 Markdown 指标表,自动标注"综合后=估算")。
- **如何验证有效**:T5/T6 四个正反用例(超容差判 FAIL、行数不匹配判 FAIL)+ **本队 Vivado 2026.1 真实综合/实现报告**解析留档。
- **边界如何确定**:GUI 复制的表格文本拒绝(须 report 输出);**golden 与被测同源**是写入 SKILL.md 的红线(自证只证确定性,不证正确性)。

#### S5. pynq-board-migration(板卡迁移 A→B,ZC702→ZC706 实例)

- **从哪些失败/观察总结**:用户在 ZC702 故障判定后拍板换用两块 ZC706(决策原文见例 2 简报「═══ 决定 ═══」节)+ **极性翻案之夜(T3)暴露的十类错误**(换板与翻案全程叙事见 raw/c09、raw/c11)。提炼时对迁移过程做了经多轮独立审查修订的完整复盘,把每个错误改写为带症状签名的通用化规则(如"『状态机复位态+计数全零+外设无反应』三连→先查物理层"),再压缩为五道门禁 G1–G5;门禁方法随包沉淀于 `skill/pynq-board-migration/references/board-delta-method.md`。
- **如何提炼**:五道门禁按序执行——G1 盘点"板耦合 vs 可移植"(口诀:**端口名随行,引脚位置永不搬运**)→ G2 从核实过的器件表换 part(`retarget_check.py --boards`,含"pynq-z2 与 zybo-z7-20 完整型号相同却是两块板"的同硅片陷阱行)→ G3 目标板 master XDC 重新生成约束并离线核对端口集合完整性 → G4 重建+时序签核 → G5 器件门禁(`--hwh --expect-part`,UNKNOWN 时 exit=2 绝不静默放行)。
- **如何验证有效**:T8a–T8e 正反双向离线实测(**"迁移漏掉一个端口必被检出"**、错误器件必被 part-gate 拦截);**目标器件 xc7z045ffg900-2 在本机完成板前门禁**:get_parts 确认存在 + 该器件真实综合冒烟通过(124s,Vivado 2026.1;执行时刻为北京时间 2026-10-25 00:05,即 UTC 2026-10-24,证据为包内 `skill/tests/VERIFICATION-2026-10-25.md`)。器件号经 UG850/UG954 核实。
- **边界如何确定**:G3 只核对端口集合与电平类变化、不验证时序(那是 G4 的事)显式声明;跨家族(7 系→UltraScale+)按 references 的增量表方法扩展;真实 ZC702→ZC706 迁移的板上环节标注 ⏳ 待板,未回填前不声称已测。

### 4.3 出处类型与证据方式

技能包各项的出处按证据方式分为三类(与 `skill/README.md` 各"来源"行的标注一致):

- **档案事故型**(有项目档案直接支撑):pynq-interface-contract(手写 MMIO 偏移两次出错与 RTL 漂移的教训;寄存器映射错序一类错误在 raw/c05 的审查往返中有实录)、pynq-golden-report(W1–W3 轮次报告收割实践与"指标禁手改"事件)、pynq-board-migration(ZC702→ZC706 真实换板,叙事见 raw/c09、raw/c11)、pitfalls B5/B6/B7(s 线四轮校验实测,见 raw/s02)。
- **模式观察型**(高频事故模式的观察与文档核对):pynq-overlay-load-verify——bring-up 期间多版本位流/诊断副本高频迭代中暴露的 ".bit/.hwh 不同源、IP 改名失配"类风险(测试 T1 即以真实时间戳差告警演示该模式);pynq-dma-coherence——缓存纪律与关键 API 事实经 UG585、PYNQ 文档与 `pynq/lib/dma.py` 源码逐条核对,错误指纹表为本队整理。
- **流程提炼型**(协作流程沉淀):prompt-workflows 两个模板(W 系列划分表与轮次报告诊断即其产物;边界如实标注:无量化目标时划分模板退化为"全放 PS",综合未通过时不适用瓶颈模板;验证为"流程在本队走通"的非统计性验证);templates(上板首触 notebook 浓缩 bring-up 自底向上验证顺序,报告骨架对照指南 3.3.5.3 证据类型)。

### 4.4 验证体系(三层,与"绝不冒充已测"原则)

| 层 | 内容 | 结果 |
|---|---|---|
| 离线测试 | `tests/run_tests.py` 18 项(含必失败反例) | 18/18 PASS(VALIDATION_LOG.md 留档) |
| MCP 端到端 | 真实驱动 Vivado:握手/11 工具/拉起/器件/**真实综合**/**真实 xsim 仿真**/优雅关闭 | 7/7 PASS(四轮闭环后,VERIFICATION-2026-10-19) |

板上环节(live 冒烟、DMA 板载基准、真实迁移 G3–G5)在验证状态表中一律标 ⏳ 待板——**✅=已在本机真实执行并留档;⏳=需要板卡,未回填前不声称已测**。这套"真实驱动 + 绝不冒充已测"的验证纪律由队长定立并贯穿三轮验证(对应 T7 的开工规矩与 4.4 的 ✅/⏳ 体系)。

### 4.5 边界确定的方法论

边界的确定与出处同等重要,方法是:①每个 SKILL.md 显式写"失效条件"节(什么输入会被拒绝/警告/跳过);②验证状态用 ✅/⏳ 二值区分,杜绝"应该可以";③事实类内容标证据等级 [A]–[E],等级只决定找线索的先后、不决定放行——极性类唯一放行 [E] 实测;④降级路径显式化(资源降级矩阵:无官方文档→极性/电压类记"未定";无 JTAG→health 判读走人眼主路径)。

## 五、AMD Ross 使用体验与改进建议(AMD Ross Usage Experience & Suggestions)

本项目把 AMD Ross(本地 Vivado MCP + 官方 amd-doc-search)作为标准工具链用了三周(c05/c07/s01/s02),以下体验与建议全部出自实测记录。

### 5.1 用得好的地方

- **双通道设计**:本地 Vivado MCP(实操:建工程/综合/报告/会话管理)+ amd-doc-search(知识:按文档编号/版本精确命中官方手册小节,附 docs.amd.com 直链)分工清晰,"回答方法论问题前先检索再作答,答案直接引官方小节,比网页搜索准确得多"(raw/c05 第38轮)。
- **真实可驱动,不是演示品**:全链路 7 项检查(握手→11 工具注册→拉起 Vivado(约 6s)→版本/器件→真实综合→真实 xsim 仿真→优雅关闭)四轮校验后 7/7 通过(VERIFICATION-2026-10-19);Z-7020 AND 门真值表 4/4 向量全对。
- **与竞赛工作流契合**:写完 RTL 直接让 MCP 跑 synth_design + report_timing_summary,"把 WNS/资源数字拿回来再改代码,不要凭空猜"(raw/c05 第38轮)——本队技能包 golden-report 的"从 report_* -file 原始输出机读"路线即由此而来。

### 5.2 实测踩到的坑

| # | 现象 | 代价 | 出处 |
|---|---|---|---|
| 1 | 握手有客户端名门禁:`clientInfo.name` 自造名字**返回 0 个工具且无报错** | 排查半天才知道是名字问题 | raw/c05 第38轮 |
| 2 | `working_dir` 含中文 → synth_design 崩溃(0xC0000374) | 服务端不预检,崩在 Vivado 深处 | raw/c05 第38轮(本机实测) |
| 3 | 长命令(综合/实现)HTTP 连接超时 ≠ 失败,Vivado 仍在跑 | 须客户端轮询 `is_command_running` 判定 | raw/c05 第38轮 |
| 4 | 服务器生命周期跟随宿主:空闲约 5 分钟自退、随宿主 shell 退出 | 每次都要"先拉起再重试" | raw/c05 第38轮、raw/s02 第1轮 |
| 5 | Vivado 不搜索 %APPDATA%\Xilinx 的许可证 | 须 `XILINXD_LICENSE_FILE` 显式指路(踩坑 B5) | raw/s01、pitfalls |
| 6 | doc-search 的 tool/version 参数是数组,传字符串被 schema 拒绝 | 参数形态无提示,靠试错 | raw/c05 第38轮 |

### 5.3 改进建议

1. **握手门禁显式报错**:客户端名不合法时返回明确错误码与合法枚举,而非静默给 0 个工具(坑 1)。
2. **working_dir 预检**:非 ASCII 路径在服务端启动前拒绝并提示,不要让 synth_design 以 0xC0000374 深埋(坑 2;本队已在踩坑清单 B6 相邻条目记录)。
3. **长命令任务化**:综合/实现提供任务句柄与进度查询的一等接口,免除客户端轮询协议(坑 3)。
4. **守护进程化**:MCP 服务器独立于宿主 shell 生命周期,空闲退出阈值可配置(坑 4)。
5. **许可证自动发现**:默认搜索 %APPDATA%\Xilinx,或首启时引导配置(坑 5)。
6. **生态空白**:公开 skill 生态中 FPGA 类集中在 Vivado Tcl/仿真/约束,PYNQ 主机侧(overlay 体检/DMA 纪律/契约生成/报告收割)是空白(raw/c02 调研结论)——建议官方补齐主机侧技能;本队技能包即为该空白的第三方填补,与 Ross 互补而非重复。
7. **报告收割结构化**:把 utilization/timing 报告解析为结构化 JSON 做成内置工具,减少每个使用者重复写解析器(本队 collect_report.py 即此需求的自证)。
